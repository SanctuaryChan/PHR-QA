# 1. 项目概述

## 1.1 项目目标（做什么）

本项目实现一个面向 **KGQA（Knowledge Graph Question Answering）** 的实验框架，核心研究点是 **Path→Subgraph Hybrid Retrieval（路径引导的子图检索）**：

* 给定自然语言问题 `q` 与题中提到的主题实体（topic entities）
* 先用 LLaMA2-7B-chat 生成若干条**关系路径规划**（relation paths，作为“方向”）
* 再在该方向附近从图中提取候选三元组集合（候选证据）
* 对候选证据进行融合打分并在预算内选出 top-N 条证据
* 把证据与问题一起交给 LLaMA2-7B-chat 输出最终答案
* 在 WebQSP / CWQ 上计算 EM/F1 等指标，对比 baseline（LLM-only / path-only / subgraph-only / hybrid）

## 1.2 非目标（不做什么）

为控制工程复杂度（尤其你是“代码小白”起步）：

* 不要求一开始接入完整 Freebase/Neo4j 等全图数据库
* 不要求一开始训练任何模块（Planner、Scorer 先用规则/轻量实现）
* 先利用数据集中每个问题自带的 `subgraph` 作为可检索图，保证快速跑通与复现

> 后续如果你想做“全图检索”或“训练 planner/scorer”，在该框架上可扩展。

# 2. 系统架构与模块划分

整体按“离线评测流水线”设计：**Data → Planner → Retriever → Reader → Eval → Report**。

## 2.1 模块列表（包含什么）

建议工程目录（供工程师参考）：

```
kgqa-hybrid/
  configs/
    webqsp.yaml
    cwq.yaml
  data/                  # 指向你的datasets路径，或软链接
  src/
    run.py               # 主入口：跑实验、写输出
    dataloader.py        # 读WebQSP/CWQ/RoG格式，统一成内部样本结构
    idmap.py             # entities.txt / relations.txt 映射加载
    graph_store.py       # 构建每个样本的局部图（subgraph）邻接表、查询接口
    planner_llama.py     # Step1：LLaMA2生成 relation paths（约束输出）
    retriever_llm_only.py
    retriever_subgraph.py
    retriever_path.py
    retriever_hybrid.py  # 你的主方法：path-guided + hybrid scoring + selection
    triple_scorer.py     # 语义分/结构分/路径对齐分，统一接口
    prompt_builder.py    # 把证据格式化成 LLaMA2 输入prompt
    reader_llama.py      # LLaMA2 推理封装（generate）
    eval.py              # EM/F1 + 其他检索指标
    cache.py             # planner缓存、证据缓存
    utils.py             # normalize、logging、seed等
  outputs/
    webqsp/
    cwq/
```

## 2.2 模块职责（每个模块干什么）

### A. dataloader（数据加载与格式统一）

* 读取 WebQSP/CWQ（GNN-RAG 格式 JSONL）
* 可选读取 RoG 格式 JSON
* 统一输出内部 `Sample` 结构（见第3章）

### B. idmap（ID ↔ 文本映射）

* 加载 `entities.txt`、`relations.txt`
* 提供：

  * `eid -> entity_mid_or_name`
  * `rid -> relation_name`
* 供 Prompt 构造与可读化输出使用

### C. graph_store（局部图构建与查询）

* 利用每条样本自带的 `subgraph.tuples` 构建局部邻接表
* 提供基本图查询：

  * `get_1hop(e)` / `get_1hop_by_rel(e, r)`
  * BFS 计算距离（含方向）
  * path-constrained traversal（按关系序列走）

### D. planner_llama（路径规划）

* 输入问题 `q` + 候选关系集合 `R_cand`
* 输出 top-k 条 relation paths（JSON 格式）
* 使用 LLaMA2-7B-chat-hf，**不训练**，用约束 prompt 降低关系名错配

### E. retriever（证据检索）

四种检索策略，统一接口 `retrieve(sample) -> evidence_triples`：

1. **LLM-only**：不提供证据
2. **Subgraph-only baseline**：对样本 subgraph 的 triples 语义打分选 top-N
3. **Path-only baseline**：用规划路径在 subgraph 上 constrained traversal，抽取路径证据
4. **Hybrid（主方法）**：用路径做候选过滤/扩展 + 融合打分（语义+结构+路径对齐）选 top-N

### F. prompt_builder（证据转文本）

* 将 triples 从 (h,r,t) 的 ID 形式转成可读文本块
* 控制 token 预算（最多 N 条、可截断）
* 输出最终给 reader 的 prompt

### G. reader_llama（答案生成）

* 输入 `prompt`（问题+证据）
* 用 LLaMA2-7B-chat-hf 生成答案文本
* 输出 `answer_text`（可选输出引用证据）

### H. eval（评测与报告）

* WebQSP/CWQ：EM/F1（字符串规范化后）
* 可加检索指标：

  * Answer-in-Evidence（答案实体是否出现在证据中）
  * Evidence size（平均 triples 数、token 数）
* 汇总写出 `outputs/*.jsonl` 和 `summary.csv`

### I. cache（缓存）

* planner 输出缓存（同一问题不重复生成 paths）
* 检索结果缓存（加速调参）

# 3. 数据集格式说明

你当前有两套格式：**GNN-RAG 格式（WebQSP/CWQ）** 与 **RoG 格式**。

## 3.1 WebQSP/CWQ（GNN-RAG 格式）文件结构

目录如下（你给的）：

* `train.json / dev.json / test.json`：**JSONL**（每行一个样本 JSON）
* `entities.txt`：实体表（行号 = entity_id）
* `relations.txt`：关系表（行号 = relation_id）
* `entity_emb_100d.npy / relation_emb_100d.npy / word_emb.npy / vocab.txt`：嵌入（可用于轻量语义打分，不依赖外部模型）

### 3.1.1 样本 JSON（JSONL 每行一条）

你给的例子（简化）：

```json
{
  "id": "WebQTest-0",
  "question": "what does jamaican people speak",
  "entities": [4648],
  "answers": [
    {"kb_id": "m.01428y", "text": "Jamaican English"},
    {"kb_id": "m.04ygk0", "text": "Jamaican Creole English Language"}
  ],
  "subgraph": {
    "tuples": [
      [4648, 430, 77418],
      [4648, 448, 77419],
      ...
    ]
  }
}
```

字段语义：

* `id`：样本 ID
* `question`：问题文本
* `entities`：topic entity 的 **整数 ID**（对应 `entities.txt` 行号）
* `answers`：答案集合（可多答案）

  * `kb_id`：Freebase MID（字符串）
  * `text`：答案文本（用于评测）
* `subgraph.tuples`：局部图三元组列表，三元组为 `[h_id, r_id, t_id]`

  * `h_id/t_id` 是 entity_id（对 `entities.txt`）
  * `r_id` 是 relation_id（对 `relations.txt`）

> **重要实现建议**：本项目第一阶段只在 `subgraph` 内检索与遍历，避免接全图带来的工程爆炸。

# 4. 内部数据结构（工程强烈建议统一）

定义内部 `Sample`（Python dict 或 dataclass）：

```python
Sample = {
  "id": str,
  "question": str,

  # topic entities（GNN-RAG: List[int]；RoG: List[str]）
  "topic_entities": list,

  # gold answers（尽量统一成文本list，便于EM/F1）
  "gold_answer_texts": list[str],

  # 可检索图：triples
  "triples": list[Triple],
}

Triple = {
  "h": int|str,
  "r": int|str,
  "t": int|str,

  # 可选：可读文本缓存（避免重复映射）
  "h_text": str,
  "r_text": str,
  "t_text": str
}
```

这样 retriever/prompt_builder/reader 全部吃同一套结构。

# 5. 各模块详细设计

## 5.1 graph_store：局部图构建与查询

### 输入

* `Sample.triples`（来自 `subgraph.tuples` 或 RoG graph）

### 输出/提供的能力

构建邻接：

* `adj_out[h] -> list[(r,t)]`
* `adj_in[t]  -> list[(r,h)]`（反向邻接，做双向结构特征）

核心 API（建议）：

* `neighbors(e, direction="out"|"in"|"both")`
* `neighbors_by_rel(e, rel, direction="out"|"in")`
* `bfs_distance(sources, max_hops, direction)`
* `constrained_traverse(sources, rel_seq, direction="out")`
  返回沿 rel_seq 走到的节点集合 + 走过的边集合（用于 path-alignment）

### 注意点

* `subgraph` 规模可能较大（几千 triples），BFS 要有 `max_hops` 限制
* 路径遍历失败要安全返回空集，不要抛异常

---

## 5.2 planner_llama：路径规划（Step1）

### 目标

用 LLaMA2-7B-chat 生成 top-k 条关系路径（relation sequences），作为“方向”。

### 输入

* `question`
* `candidate_relations`（强烈建议从该样本 subgraph 中统计得到，减少错配）

生成候选关系集合方式：

* 从 sample triples 抽取 unique 的 `r_text`，得到 `R_cand`
* 如果太多，按频率取 top-M（如 M=80/120）

### 输出格式（必须 JSON，便于解析）

```json
{
  "paths": [
    {"rels": ["rel_a","rel_b"], "score": 0.81},
    {"rels": ["rel_c"], "score": 0.63}
  ]
}
```

### Prompt 关键约束（要点）

* 明确：**只能从候选关系列表中选择**
* 明确：输出必须是 JSON
* 明确：每条 path 的长度范围（WebQSP 1–2；CWQ 2–4）
* 明确：输出 top-k 且尽量多样（首关系不同）

### 实现建议

* 支持 planner 缓存：`cache/planner/{dataset}/{id}.json`
* planner 失败/解析失败时：

  * fallback：选 `R_cand` 里与问题词重叠最高的关系（简易规则），保证 pipeline 不崩

---

## 5.3 triple_scorer：融合打分（模块C关键）

我们把总分拆成三部分，方便 ablation：

[
s(t)=\alpha s_{sem}(t)+\beta s_{path}(t)+\gamma s_{struct}(t)
]

### 5.3.1 语义分 `s_sem`

为了避免外部模型下载，建议优先用数据集自带 embedding：

* `vocab.txt + word_emb.npy`：问题向量

  * tokenize：lowercase + split
  * 查 vocab index，取平均 word embedding 得 `q_vec`
* `entity_emb_100d.npy + relation_emb_100d.npy`：三元组向量

  * `t_vec = emb(h) + emb(r) + emb(t)`（或 concat+MLP，先用加和）
* 语义相似：cosine(q_vec, t_vec)

> 这是最“工程友好”的 subgraph baseline/semantic scorer。

### 5.3.2 路径对齐分 `s_path`

核心思想：三元组是否与 planner 规划的路径一致。

实现（从易到难）：

**版本 v1（最简单，先上）**

* 若 triple 的 `r_text` 出现在任意规划 path 的关系集合中：`s_path=1` 否则 0
* 或按出现次数/规划 path 置信度加权

**版本 v2（更准）**

* 对每条规划 path，做 constrained traversal 得到“被该 path 触达的边集合”
* 若 triple 在这些边里：给更高分
* triple 与 path hop 位置一致可加分（例如 rel 出现在第2跳）

### 5.3.3 结构分 `s_struct`

用局部图结构给“位置合理性”加先验：

最推荐的两个结构特征（无需 GNN）：

1. **距离特征**：BFS 距离 topic entity 的最短距离

   * `dist_out`、`dist_in`（双向）
   * 越近分越高（或用 `1/(1+dist)`）
2. **hub 惩罚**：连接度太高的节点相关 triple 降权（减少噪声）

结构分可先做规则：

* `s_struct = 1/(1+min_dist_to_topic)`  × hub_penalty

## 5.4 retrievers：四种检索策略

统一接口：

```python
evidence = retrieve(sample, graph_store, planner_output, scorer_config) -> list[Triple]
```

### 5.4.1 LLM-only

* evidence = []
* prompt 只给 question

### 5.4.2 Subgraph-only baseline

* 候选 = sample.triples（全 subgraph）
* `score = s_sem`
* 选 top-N

### 5.4.3 Path-only baseline

* planner 生成 top-k path
* 对每条 path：

  * 从 topic_entities 出发 constrained traverse
  * 收集 traversal 经过的 triples
* 合并去重后，若超过 N，再按 `s_sem` 或 path 置信度排序取 top-N

### 5.4.4 Hybrid（主方法）

核心流程（推荐实现顺序）：

**Hybrid v1（最小可行，强烈建议先做）**

1. planner 得到 paths
2. 用“关系集合过滤”：

   * `R_plan = union(paths.rels)`
   * 候选 `T_cand = {t in triples | t.r in R_plan}`
3. 对 `T_cand` 计算总分 `s = α sem + β path`（struct先不加也行）
4. 选 top-N

**Hybrid v2（标准版）**

1. 基于 paths 做 constrained traversal 得到触达节点/边
2. 候选池扩展：保留

   * path 边
   * path 触达节点的 1-hop 邻域（解决“断路/缺桥”）
3. 总分 `α sem + β path + γ struct`
4. 预算内选 top-N（可加 diversity：不同关系/不同节点覆盖）

> 这样能稳定体现 “path 高精度 + subgraph 高召回” 的融合优势。

## 5.5 prompt_builder：证据格式化

### 输入

* question
* evidence triples（已映射成可读文本）

### 输出 prompt（建议结构）

* 系统指令：只能基于给定证据回答；证据不足就说不知道
* 证据块：每条 triple 一行
* 问题：原问题
* 输出格式：只输出答案（或 “答案 + 简短依据”）

示例（伪）：

```
You are answering a question using the provided knowledge graph triples.
If the answer is not supported by the triples, say "Unknown".

Triples:
1. (Jamaica, /location/country/official_language, Jamaican English)
2. ...

Question: what does jamaican people speak
Answer:
```

### Token/预算控制

* 证据条数 N（WebQSP 推荐 40；CWQ 推荐 80 起步）
* 过长实体/关系名可做简化（截断、别名）

---

## 5.6 reader_llama：LLaMA2 推理封装

建议支持：

* batch 推理（按 GPU 能力）
* generation 参数配置（max_new_tokens、temperature、top_p）
* 输出清洗（去掉多余解释）

工程上建议把 model 加载放到单例，避免重复初始化。

---

## 5.7 eval：评测

### WebQSP/CWQ EM/F1（建议复用 baseline 的 normalize）

* normalize：lowercase、去标点、去冠词、合并空格
* EM：预测答案是否与任一 gold 完全匹配
* F1：token-level overlap（多答案取 max）

### 可选检索指标（强烈建议做）

* **Answer-in-Evidence**：

  * 若 gold 有 `kb_id`：检查 evidence 中是否出现相同 MID（需 entities.txt 映射到 MID）
  * 或检查 evidence 文本是否包含 gold answer text（弱但简单）
* evidence size/token 统计

输出文件建议：

* `outputs/{dataset}/{split}/{method}.jsonl`：逐样本记录
* `outputs/{dataset}/{split}/summary.csv`：总表

# 6. 开发顺序（从最简单跑通到逐步融合）

这是你最关心的部分。我给一个**工程师可执行的阶段计划**，每阶段都有“验收标准”。

## Phase 0：环境与数据连通（0.5–1天）

**目标**：能读取数据、打印样本信息

* 实现 `dataloader` 读取 JSONL
* 实现 `idmap` 能把 entity_id/relation_id 映射为文本
* 验收：打印前 10 条样本的 question、topic entity 文本、subgraph triple 数量

---

## Phase 1：LLM-only 跑通评测（1天）

**目标**：最小闭环（data → llama → eval）

* `retriever_llm_only`：evidence=[]
* `prompt_builder`：仅 question
* `reader_llama` + `eval`
* 验收：能在 dev/test 跑完并输出 EM/F1（哪怕很低）

---

## Phase 2：Subgraph-only baseline（2–4天）

**目标**：证据注入闭环

* `graph_store`：构建 subgraph 邻接
* `triple_scorer.s_sem`：用自带 embedding 做语义打分
* `retriever_subgraph`：从 subgraph triples 选 top-N
* 验收：Subgraph-only 的 EM/F1 > LLM-only（通常能做到）

---

## Phase 3：Planner（Step1）接入（2–4天）

**目标**：能稳定输出可解析的 relation paths

* `planner_llama`：输入 question + candidate relations（来自 subgraph）
* 做缓存与 fallback
* 验收：对 100 条样本，解析成功率 > 95%

---

## Phase 4：Path-only baseline（2–4天）

**目标**：实现 path-constrained traversal 证据抽取

* `graph_store.constrained_traverse`
* `retriever_path`：按规划 path 找路径证据
* 验收：能跑完 dev/test，得到 path-only EM/F1（作为对照）

---

## Phase 5：Hybrid v1（3–7天）

**目标**：主方法最小版上线（先出论文主趋势）

* `retriever_hybrid v1`：

  * 用 `R_plan` 过滤 triples
  * 总分 `α sem + β path_presence`
  * 选 top-N
* 验收：Hybrid v1 在 CWQ（复杂集）对比 subgraph-only / path-only 有可见提升或至少接近但证据更干净（后面可靠 v2 拉开）

---

## Phase 6：Hybrid v2（7–14天）

**目标**：标准版（能在复杂问题显著获益）

* path traversal 得到触达节点/边
* 候选池扩展：path邻域 1-hop 补桥
* 加入结构分 `s_struct`
* 加入简单 diversity（避免 top-N 全是同一关系/同一hub）
* 验收：CWQ 上 hybrid v2 通常能比 v1 更稳；同时 evidence 噪声更少

---

## Phase 7：调参、消融、报告自动化（持续）

* 网格搜索：k（paths 数）、h（扩展半径）、N（证据条数）、αβγ
* 输出 cost 曲线：性能 vs token
* ablation：去 path / 去 struct / 去 candidate filtering

# 8. 工程风险点与规避（提前写给工程师）

1. **Planner 输出不可解析/关系名错配**

* 强制候选关系列表 + JSON 输出
* 加缓存 + fallback

2. **subgraph 太大导致 BFS/遍历慢**

* 限制 max_hops、候选池上限
* 优先用“过滤”再“扩展”，别全量打分

3. **LLaMA2-7B 推理慢**

* 先在小样本 dev 子集跑通
* 后续可接 vLLM / 量化（这是工程优化，不影响论文核心）

4. **评测脚本不一致**

* 优先复用你已复现 baseline 的 eval 逻辑（保证可对比）
